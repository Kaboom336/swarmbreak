---
name: roblox-game-production
description: Develop Roblox games from an idea through polished prototypes, large content and multiplayer projects, and live updates. Use for new games, substantial direction changes, or establishing and scaling a repeatable game production system.
---

Translate the user's idea into something players can understand, do, and want to repeat. Success requires playable and visual evidence; neither a long feature list nor passing unit tests proves a good game.

1. Read the project's instructions, current brief, research, code state, and existing art before changing direction. Preserve useful work when rebuilding. Resolve scope from the conversation; ask only about missing decisions that materially affect the result. Record budget, script-import restrictions, target devices, build destination, and commit/publish rules in the project brief.
2. Fill [the brief](assets/game-brief.md) with the player fantasy, repeated verbs, social interaction, first-session route, art language, and the next playable milestone. Separate user requirements from proposed choices and timing hypotheses.
3. Research comparable games and reusable foundations. Use [source evaluation](references/source-evaluation.md). Compare how the mechanic feels and why friends affect play, rather than copying a game's surface. Label listing claims, inspected code, watched footage, and tested behavior separately. Select a foundation only after checking actual fit and license; do not force a mismatched template merely because it is complete.
4. Follow [production gates](references/production-gates.md) for the current stage. For a new game, make one complete loop with final-direction art before scaling content. For an established game, use a representative feature slice and protect working systems; do not restart prototyping the entire game. Reuse tested commodity code and licensed kits; author the focal object, its state changes, and the signature interaction deliberately.
5. When work spans substantial content, multiple places, teams, persistent economies, or live releases, read [scaling production](references/scaling-production.md). Choose controls from actual risks, not projected ambition. Track architecture decisions, dependency ownership, content budgets, milestones and release evidence in durable project files rather than conversation memory.
6. Implement, verify, build, and provide a short playtest route. For a Windows Rojo/Rokit/Lune project, [verify-project.ps1](scripts/verify-project.ps1) runs pinned local tools and records a build hash for one place. Its paths are configurable; it is not a complete multi-place CI system. Other projects should use their existing checks. A build report must distinguish static checks from runtime, visual, device, and fun evidence. Do not claim Studio or screenshots were inspected without doing so.
7. Update the brief with evidence, remaining shortcomings, and the next area to improve. Give the user a runnable artifact after gameplay changes and specific checks they can perform without terminal work. Commit, upload, purchase, message others, or publish only within the user's authorization.

When the user requests a gauntlet process or authorized agent review, use [gauntlet execution](references/gauntlet-execution.md) for substantive gameplay and system changes. It adapts separated implementation and fresh acceptance review to available collaboration tools, keeps runtime gaps explicit, and tracks bounded tasks in a project-local workbench. Tiny routine edits need only proportionate checks; this reference does not authorize delegation by itself.

When available, prefer a connected Roblox Studio integration for tree inspection, play mode, console, and screenshots. Otherwise use the user's clips/screenshots and local build checks, documenting runtime gaps. The official Studio MCP is an integration option, not a dependency that may be assumed present.

Apply project preferences locally. A Pumpkin-specific free-only budget, Halloween style, or no-script Creator Store rule should not silently become a restriction for unrelated future games. Keep a source/asset ledger and preserve required license notices for every adopted dependency.

Keep this skill focused on Roblox. Its production habits can inform other projects, but select the appropriate platform workflow rather than applying Roblox services or this Windows build helper to unrelated applications. Verify current API behavior, service quotas, licensing and tool availability when relevant; avoid freezing today's library or platform limits into permanent instructions. Refine the workflow from measured outcomes without accumulating rules from every one-off failure.
